# Webapp

The webapp bundled with `waymark-executor` shows workflow progress and node
load. Use it to find a stuck run, inspect its action calls, or check whether
workers are keeping up with queued work.

## Enable it {{ id: 'enable-it' }}

Two environment variables on `waymark-executor`:

```bash
export WAYMARK_HTTP_ENABLED=true
export WAYMARK_HTTP_ADDR=0.0.0.0:24119  # the default
```

Restart `waymark-executor` and the webapp is live on port `24119`. The same
port serves the HTTP API under `/api`, with interactive API docs at
`/api/docs`, and a `/healthz` endpoint for load balancer checks.

<Note>
The HTTP server binds to `0.0.0.0` by default and has no built-in auth.
Keep the port on your private network or behind your existing auth
proxy.
</Note>

## What it shows {{ id: 'what-it-shows' }}

The webapp reads recorded workflow events and node load samples. Some details
are unavailable or inferred:

- **No arguments, results or exception messages.** They aren't recorded,
  so the webapp says "Not recorded" rather than showing an empty value.
  An exception appears by its type only.
- **Workflow names come from registration.** When a name wasn't recorded,
  the workflow is identified by its id.
- **Retries are inferred.** Attempt numbers aren't recorded; a call that
  repeats an earlier one is marked as an inferred retry.
- **No controls.** There's no requeue, cancel or schedule management.
  Manage schedules with the [scheduling API](/python/scheduling).

Views refresh every few seconds and show how fresh their data is. Workflow
time and state filters are in the search dropdown. The Fleet view has its own
time window control.

## Instances {{ id: 'instances' }}

The Workflows view lists instances in the selected time window, with problems
first. Each row shows the state, workflow name and id, current activity,
timeline, and elapsed time.

Search by workflow name, instance id, node id, or state. Select a row to open a
preview. Pausing the list holds its rows in place while their workflow details
continue to update.

An instance's state is derived from its events, and the rule behind each
state is shown when you hover it:

| State | Meaning |
| --- | --- |
| Active | Running now, with recent events. |
| Suspended | Waiting on an action call or a sleep. |
| Completed | Finished with a result. |
| Unhandled exception | Finished with an exception nothing caught. |
| Run error | Its last run stopped with an error. The workflow has no outcome yet and may be picked up again. |
| Cancelled | Its last run was cancelled. This doesn't mean the workflow was cancelled. |
| Unknown | No outcome, and no recent events. |

A failed action that the workflow catches doesn't make the instance
failed, so there's no "failing" state: rejected calls are counted next
to the state instead.

## Instance detail {{ id: 'instance-detail' }}

The detail view shows action calls and sleeps on a timeline, grouped by run.
Each bar spans the time from dispatch to completion, including time queued
for a worker. Saved snapshots and inferred retries are marked.

Select a call to inspect its events. The page also includes the raw event log,
gaps in that log, and the reason each run stopped.

## Fleet {{ id: 'fleet' }}

The Fleet view shows load across your nodes: action calls in flight
against total worker capacity, calls queued for a worker slot (with the
95th percentile wait), completions per second, and action handling time.
Below are rows for each node boot and charts of in-flight and queued calls
over the time window. When you're deciding whether to add nodes or raise
`WAYMARK_CONCURRENT_PER_WORKER`, these are the numbers to look at.

## Operating notes {{ id: 'operating-notes' }}

How far back the webapp can look is bounded by the observability
retention: seven days by default, set by
`WAYMARK_OBSERVABILITY_EVENTS_RETENTION_MS` and
`WAYMARK_ESSENTIAL_METRICS_RETENTION_MS` - see
[Configuration](/guides/configuration#observability).

In a multi-container deployment, enable the webapp where
`waymark-executor` runs and publish port `24119`; the
[Production Deployment](/guides/production) compose file does exactly
this.
