# Production Deployment

A production Waymark deployment is three pieces: your application, one or
more nodes, and Postgres. It should be basically plug and play with any stack: self-hosted
or in the cloud. There's no broker to host, no scheduler service, no replay servers. Postgres
holds every piece of shared state, and everything else is a stateless container you can
kill and restart at will, outside an [upgrade](#upgrades).

## Topology {{ id: 'topology' }}

- **Your app** is whatever serves traffic today - a FastAPI service, a
  script, a cron job. It queues workflows when it wants to delegate processing to the job cluster. The SDK boots a singleton
  `waymark-bridge` inside the container on first use, so the app needs
  nothing beyond a connection to the database. The bridge never changes
  the database schema, so its database role only needs to read and write
  rows.
- **The node** is one container running `waymark-executor`. It runs your
  workflows, dispatches their actions to a pool of Python worker
  processes, and persists every step in Postgres. It also runs the
  scheduler and, if you enable it, serves the HTTP API and the webapp.
- **Postgres** is the only stateful piece. Anything 14+ works, including
  the managed instance you already have.

Your app and the nodes coordinate purely through Postgres, so they don't
need to reach each other over the network. Scale them and restart them
independently; only an [upgrade](#upgrades) needs an order.

## Migrations and upgrades {{ id: 'upgrades' }}

The nodes migrate the database schema at startup and, with the HTTP
server enabled, serve `/healthz` only once that is done. The bridge only
checks the schema, and only when it starts: it waits for a migration in
progress to finish, for up to `WAYMARK_MIGRATIONS_STATEMENT_TIMEOUT_MS`,
then refuses to start unless the schema matches its own migrations
exactly, neither older nor newer. A node with older migrations refuses
the same way. The bridge's check of the observability store's schema
works likewise, for up to
`WAYMARK_OBSERVABILITY_POSTGRES_MIGRATIONS_STATEMENT_TIMEOUT_MS`.

On a new database, start the app once a node is healthy. Until then,
your app's workflow calls fail with `unable to boot waymark server`, and
each call tries again. The same error shows when the app and the nodes
run releases with different migrations.

A workflow call waits about 5 seconds for the bridge the SDK starts. While
a migration is in progress, the call fails with that error even though
the bridge itself keeps waiting for the migration. The bridge the SDK
starts keeps no logs, so the error does not say why the bridge did not start
([#820](https://github.com/piercefreeman/waymark/issues/820)); to see
the reason, run `waymark-bridge` by hand with the app's environment.

To upgrade, stop every container that runs the app, every
`waymark-bridge` wherever it runs (the SDK starts it as a process of its
own, which outlives the app's), and every node, all at once rather than
in a rolling update: neither a bridge nor a node that is already running
checks the schema again. Then start the nodes on the new version, and
start the app on the new version once a node is healthy. Your app is
down for the whole upgrade. There is no going back: the old version
refuses the migrated schema, so snapshot the database before you
upgrade.

## Share an image {{ id: 'one-image' }}

Build a single image that contains your application code and the
waymark package. They're both referencing the same underlying workflow and
action code, so it makes sense for the image to have parity. The app and
`waymark-executor` only need different commands in the entrypoint.

If you already have Dockerfile, you just need a new service that mounts
with `waymark-executor`. If you don't already have one, this basic one should
get you started.

```dockerfile
FROM python:3.12-slim

RUN pip install uv

WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
COPY src ./src

ENV PATH="/app/.venv/bin:${PATH}"

# The default command serves the app; `waymark-executor`
# overrides it.
CMD ["uvicorn", "yourapp.web:app", "--host", "0.0.0.0", "--port", "8000"]
```

## Compose the services {{ id: 'compose' }}

The same shape works in Docker Compose, Kubernetes, or anything that runs
containers. In Compose:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
    volumes:
      - postgres-data:/var/lib/postgresql/data

  executor:
    build: .
    command: ["waymark-executor"]
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      WAYMARK_DATABASE_URL: postgresql://app:app@postgres:5432/app
      WAYMARK_USER_MODULE: yourapp.workflows
      WAYMARK_HTTP_ENABLED: "true"
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:24119/healthz')"]
      interval: 5s
      start_period: 60s
    ports:
      - "24119:24119"

  app:
    build: .
    depends_on:
      executor:
        condition: service_healthy
    environment:
      WAYMARK_DATABASE_URL: postgresql://app:app@postgres:5432/app
    ports:
      - "8000:8000"

volumes:
  postgres-data: {}
```

## Production settings {{ id: 'production-settings' }}

The defaults are tuned for a single host. Tuning in production is usually governed by:

| Variable | What it controls |
| --- | --- |
| `WAYMARK_WORKER_COUNT` | Python worker processes per node. Defaults to host CPU count to effectively allow Python to saturate each core. |
| `WAYMARK_CONCURRENT_PER_WORKER` | Concurrent actions per worker. Raise it for IO-bound actions like api requests. |
| `WAYMARK_MAX_CONCURRENT_INSTANCES` | Workflow instances one node holds at once. |
| `RUST_LOG` | The node's log filter, e.g. `info` or `warn`. |

If a third-party library leaks memory inside your actions, set
`WAYMARK_MAX_ACTION_LIFECYCLE` to recycle workers after a fixed number of
actions. Today the old worker is stopped with its in-flight actions,
which fail with `ActionExecutionLost`
([#727](https://github.com/piercefreeman/waymark/issues/727)); a retry
policy that lists it retries them.

Every other variable, the workload pinning lease and the scheduler
interval among them, is documented in [Configuration](/guides/configuration).

## Database connections {{ id: 'database-connections' }}

Budget your Postgres connections per process:

- **Each node** opens up to 25 connections for its main pool
  (`WAYMARK_DATABASE_MAX_CONNECTIONS`), plus up to 4 + 4 for the
  observability store's write and read pools - 33 in total, since the
  observability store shares the main database by default. At startup it
  also opens one connection for the main migrations and one for the
  observability migrations; each is closed before the pools of its
  database open, so neither adds to the 33.
- **Each app container, pod or host** (whatever shares one `localhost`)
  that queues workflows runs one singleton bridge, shared by its
  processes, with
  up to 10 connections (`WAYMARK_DATABASE_MAX_CONNECTIONS`, the same
  variable as the node's, with a default of its own), plus up to 4 for
  its own observability write pool - 14 in total. At startup it also
  opens one connection to check the main schema and one to check the
  observability schema; each is closed before the pool of its database
  opens, so neither adds to the 14.

The observability store holds events and node load samples, kept for
seven days by default. On a busy deployment you can move it off the main
database by pointing `WAYMARK_OBSERVABILITY_DATABASE_URL` at another
Postgres, and its reads at a replica with
`WAYMARK_OBSERVABILITY_READ_DATABASE_URL`; the node's own connection
count stays the same. Every host that boots the bridge, the SDK's
included, then carries the same `WAYMARK_OBSERVABILITY_DATABASE_URL`:
without it the bridge looks for the store in the main database and
refuses to start. Once the nodes run on the new store, drop the old
`observability` schema from the main database: a bridge still pointed at
it would find a store at the right migrations, pass its check, and write
where nothing reads. See
[Configuration](/guides/configuration#observability).

## Logs, metrics and the webapp {{ id: 'observability' }}

The node logs to standard output, filtered by `RUST_LOG`. It always
serves a metrics endpoint on port `9118` (`METRICS_ADDR`): `/metrics` in
the Prometheus format, and `/health`, which answers once the endpoint is
up, before the migrations run, so it tells you the process is alive, not
that the node is ready; readiness is `/healthz`. Setting
`WAYMARK_HTTP_ENABLED=true` also serves the HTTP API, the
[webapp](/guides/webapp) and `/healthz` on port `24119`.

<Note>
Neither port has authentication, and both bind to `0.0.0.0` by default.
Keep them on your private network, or firewall the hosts running
`waymark-executor` so they are not exposed to the open Internet. We
suggest the latter since there's usually no reason why nodes have to be
externally accessible.
</Note>

## Scaling out {{ id: 'scaling-out' }}

The first approach to scale is to run another node on a fresh box. Each
node claims workflow instances through a lease in Postgres that it keeps
refreshing, and a crashed node's leases expire (15 seconds by default)
for another node to pick its instances up from their last persisted
state. Your app tier
scales the same way it always has - queueing a workflow is just a
database write.

The same mechanism is what makes deploys safe, outside an
[upgrade](#upgrades). When a node container is
killed mid-run, its instances resume on another node from where they
were. An action call that was in flight on the killed node is
redelivered by the node that resumes the workflow, so the action may run
twice: make actions idempotent. A worker process dying or being recycled
on a live node is the other case: the calls it was running fail with
`ActionExecutionLost`,
or `ActionExecutionNotStarted` if it provably never started.
`ActionExecutionLost` derives from `BaseException`, so only a
[retry policy](/python/retries) that lists it retries the call;
`ActionExecutionNotStarted` is retried like any other exception. Without
a matching policy, the exception propagates like any other.

On a termination request to the node process (`SIGTERM`, what `docker
stop` and Kubernetes send, or `SIGINT`), a node shuts down gracefully:
it lets its in-flight action calls finish, releases its workflows for
another node to resume, then exits. Nothing inside the node bounds how
long that takes; your orchestrator's grace period does
(`stop_grace_period` in Compose, `terminationGracePeriodSeconds` in
Kubernetes), and a node it kills once that runs out is picked up as
described above. On Linux and macOS, further shutdown requests while the
node is shutting down do nothing today; this may change.

A Ctrl+C typed in the terminal running `waymark-executor` reaches its
worker processes too, and they stop at once: their in-flight action
calls fail with `ActionExecutionLost`
([#827](https://github.com/piercefreeman/waymark/issues/827)). On
Windows, a second Ctrl+C during the shutdown terminates the node at once
([#826](https://github.com/piercefreeman/waymark/issues/826)), and
closing its console, logging off or shutting Windows down terminates it
after the system's own timeout, or at once during a shutdown already
under way.

When Postgres is the bottleneck, you'll see it in queue latency long
before correctness suffers. Until then, one database is all the
infrastructure Waymark asks for. On very large deployments, we've seen some users
benefit from adding another separate Postgres service that just owns Waymark jobs.
Either way you should also make sure that you've tuned Postgres properly, which
we can also [help with](https://www.autopg.sh/).
