# Introduction to Python

Python actions receive serialized inputs in a worker process. Their type hints
tell the worker how to restore those inputs, and `Depends` supplies resources
such as database sessions. The workflow coordinates those calls and keeps
their results as durable state.

If you haven't read it yet, the [Quickstart](/python/quickstart) is the fastest
way to get a working setup, and
[Workflows & Actions](/python/workflows-and-actions) covers the behavior of
workflows and actions in more depth.

## Inputs and outputs {{ id: 'inputs-and-outputs' }}

Actions and workflows can run on different servers. Waymark serializes the
values passed between them so it can store those values in Postgres and send
them to another process.

Waymark's Python serializer handles most of the objects you'll use day to day: pydantic
models, dataclasses, primitives, lists, tuples, sets and frozensets, dicts, enums,
UUID, datetime, date, time, timedelta, Decimal, bytes, Path, and exceptions. One
constraint to know: dict keys must be strings: a dict keyed by ints or
tuples fails at serialization time. Some of these types arrive in a different shape
unless the receiving parameter's annotation restores them - see
[Known issues](/python/control-flow#known-issues).

For anything richer than a couple of scalars, declare a pydantic model:

```python
from datetime import datetime, timezone

from pydantic import BaseModel, Field
from waymark import action

from myapp.models import User

class FetchUsersRequest(BaseModel):
    user_ids: list[str] = Field(min_length=1)
    include_deactivated: bool = False

class FetchUsersResult(BaseModel):
    users: list[User]
    fetched_at: datetime

@action
async def fetch_users(request: FetchUsersRequest) -> FetchUsersResult:
    users = await db.user.fetch_many(
        ids=request.user_ids,
        include_deactivated=request.include_deactivated,
    )
    return FetchUsersResult(users=users, fetched_at=datetime.now(timezone.utc))
```

These models work like FastAPI request and response models. Type checkers can
inspect their fields during development, and the worker validates incoming
data before passing it to the action.

For tiny actions, plain types are fine:

```python
@action
async def compute_factorial(n: int) -> int:
    ...
```

## Type hints and validation {{ id: 'type-hints' }}

Type checkers such as ty, mypy, and pyright can check action signatures.
At runtime, the worker also uses those annotations to restore incoming values:

- Pydantic models are validated with `model_validate`. A malformed payload
  fails the action attempt before the handler body runs.
- Dataclasses are rebuilt field by field; containers are coerced element by
  element.
- Types such as `datetime`, `UUID`, `Decimal`, and `bytes` are restored from
  their serialized form, and an enum annotation turns the serialized value
  back into the enum member.
- An argument without an annotation is passed through as received.

Workflow `run()` inputs are bound to the `run()` signature when you
queue the workflow, and its defaults are filled in there. A misnamed or
missing argument, or an extra positional one, raises `TypeError` at the
call site.

## Dependency injection {{ id: 'dependency-injection' }}

Actions can declare common dependencies the same way Mountaineer and FastAPI
controllers do - via `Annotated[T, Depends(provider)]` parameters:

```python
from typing import Annotated
from waymark import Depends, action

@action
async def send_email(
    to: str,
    subject: str,
    emailer: Annotated[EmailClient, Depends(get_email_client)],
) -> EmailResult:
    return await emailer.send(to=to, subject=subject)
```

Dependency providers can have dependencies of their own. You can reuse the
providers from a FastAPI app, including database sessions and cached clients.

A dependency is resolved per action invocation by the worker that
runs it. That means the lifecycle of any per-request resource
(database session, scoped HTTP client) is handled the same way you'd
handle it inside a web handler. If your provider is itself async, that
works - the resolver awaits it.

Workflow bodies do **not** take injected dependencies. They never run
in a Python worker - the body is compiled to IR, and the node's runtime
executes the compiled program. If your workflow needs data that relies on a dependency, fetch it
inside an action and pass the result through.

## Async / await {{ id: 'async-await' }}

Both actions and workflow `run()` methods must be async. Waymark doesn't
dispatch synchronous functions as actions.

<Note>
Declaring a function `async` doesn't make blocking work yield. A long
calculation with no `await` can hold up other actions on the same worker's
event loop. Use async I/O when available; Waymark also runs separate worker
processes for parallel execution.
</Note>

For a blocking synchronous library, call `asyncio.to_thread(...)` inside the
action to move that work off the event loop:

```python
import asyncio

@action
async def render_pdf(report: Report) -> bytes:
    return await asyncio.to_thread(_render_pdf_sync, report)
```

Inside a workflow, awaiting an action compiles to a dispatch instruction. You
can also split a long `run()` into async helper methods on the workflow class.
Their bodies follow the same compiler rules as `run()`.

```python
@workflow
class OnboardUserWorkflow(Workflow):
    async def run(self, user_id: str) -> OnboardResult:
        profile = await self._provision(user_id)
        await self._notify(profile)
        return await build_onboard_result(profile)

    async def _provision(self, user_id: str) -> Profile:
        account = await create_account(user_id)
        return await create_profile(account)

    async def _notify(self, profile: Profile) -> None:
        await send_welcome_email(profile.email)
        await enqueue_drip_campaign(profile.id)
```

Use `asyncio.gather(...)` for parallel calls and `asyncio.sleep(...)` for durable
waits. See
[Control Flow](/python/control-flow) for the full list of supported
patterns.

## Module preloading on workers {{ id: 'module-preloading' }}

Each action call carries the name of the module the action is defined
in, and a worker imports that module the first time it runs one of its
actions. So the modules only have to be importable by the workers: from
the directory `waymark-executor` is started in, or installed in its
environment. `WAYMARK_USER_MODULE` makes each worker import them at
startup instead: the first action after startup doesn't pay for the
import, and a module that fails to import then stops `waymark-executor` from
starting, after its 15 second worker attach timeout, rather than failing
the first action that needs it.

```bash
export WAYMARK_USER_MODULE=myapp.workflows
uv run waymark-executor
```

For a multi-module project, list them all:

```bash
export WAYMARK_USER_MODULE=myapp.workflows.billing,myapp.workflows.email
```

## Where workflows differ from actions {{ id: 'where-workflows-differ' }}

A few Python-specific things worth knowing about workflow `run()`
bodies that don't apply to actions:

- **No f-strings.** Build formatted values inside an action.
- **Only data-only models and dataclasses can be constructed.** The compiler
  represents them as dictionaries and binds every field before lowering. It
  rejects factories, custom or inherited initialization hooks, validators,
  computed fields, field aliases, and open generics. Literal container defaults
  are preserved. Construct richer objects inside an action.
- **Most module-level globals are off limits.** Enum members and
  exception classes resolve fine; other module-level names are rejected
  when the workflow is compiled. Pass values in as workflow inputs or
  fetch them inside an action.
- **No injected dependencies.** Workflow `run()` doesn't get
  `Depends(...)` resolution. The body is compiled, never run as Python.

The compiler diagnostic is raised the first time the workflow is run or
scheduled. When the SDK rejects a pattern it raises an
`UnsupportedPatternError` that points at the offending node and offers a
fix; when the runtime rejects one, the call raises a plain `RuntimeError`
whose message carries what the runtime could not lower (under pytest,
`workflow.run(...)` raises the gRPC error itself; see
[Exceptions](/python/api/exceptions)). The
[Control Flow guide](/python/control-flow) walks through the patterns
that *are* supported, with examples for each, and lists the
[known issues](/python/control-flow#known-issues), including remaining runtime and value-transport limitations.
