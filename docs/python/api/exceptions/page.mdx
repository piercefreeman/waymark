# Exceptions

The exception classes Waymark raises out of the SDK. You'll hit these
when a workflow is compiled or at the call site of `workflow.run(...)`.

## Unsupported patterns

Raised when the compiler hits something in your `run()` body it can't
lower to IR - the first time the workflow is run or scheduled. This is
the exception you'll see most while authoring: it carries a message, the
source line and column, and a recommendation for how to restructure. See
[Control Flow](/python/control-flow) for the supported and rejected
patterns.

A pattern the SDK accepts can still be rejected by the runtime's own
compiler when the workflow is registered. That rejection is not an
`UnsupportedPatternError` but a plain `RuntimeError`: `register_workflow
failed: …` from `workflow.run(...)`, `Failed to register schedule: …`
from `schedule_workflow(...)`. Its message carries what the runtime could
not lower. A typed exception for it is tracked in
[#821](https://github.com/piercefreeman/waymark/issues/821). Under
pytest, `workflow.run(...)` raises the gRPC error itself instead, a
`grpc.aio.AioRpcError` without the prefix
([#825](https://github.com/piercefreeman/waymark/issues/825)). It also
boots the bridge in memory mode, with no database, and a bridge already
running is reused whatever its mode
([#828](https://github.com/piercefreeman/waymark/issues/828)). Against an
in-memory bridge, `schedule_workflow(...)` fails before the runtime
compiles the workflow, with `Failed to register schedule: …` carrying `bridge running
in memory mode`.

::: waymark.ir_builder.UnsupportedPatternError

---

## Workflow failure

A workflow whose action fails without a matching retry or `try/except`
fails as a whole. The `await workflow.run(...)` call raises a
`WorkflowFailedError` whose `exception_value` is the exception the
workflow raised, as the VM models it. Handle expected failures inside the
workflow with `try/except`; treat a `WorkflowFailedError` at the call site
as the unexpected case.

::: waymark.exceptions.WorkflowFailedError

::: waymark.serialization.ExceptionValue

## VM runtime exceptions

Proxies for the three exceptions the VM raises inside a workflow when an
action attempt times out, is lost, or never starts. Nothing in this
module matters at runtime: the real exceptions are defined in Rust and
exist only in the VM, which matches them against `except` clauses by
class name and bases. The classes exist so a workflow body can spell
them in an `except` clause and so type hints have something to point at;
Waymark never raises them in Python. The retry consequences are in
[Retries & Timeouts](/python/retries#filtering-by-exception).

::: waymark.vm_exceptions.ActionTimeout

::: waymark.vm_exceptions.ActionExecutionLost

::: waymark.vm_exceptions.ActionExecutionNotStarted

---

## Retry exhaustion

Defined for retry-budget exhaustion, and exported as `ExhaustedRetries`
too. Today, exhausting a `RetryPolicy` surfaces the action's own final
exception through the workflow rather than raising this class; catch the
underlying exception type in your workflow `try/except`.

::: waymark.exceptions.ExhaustedRetriesError

---

## Schedule conflicts

Defined, but not raised today: registering a schedule name that already
exists replaces that schedule rather than conflicting with it, and a
failed schedule call raises `RuntimeError`. See
[Scheduled Workflows](/python/scheduling).

::: waymark.exceptions.ScheduleAlreadyExistsError
