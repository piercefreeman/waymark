# Workflow

The `Workflow` base class is the durable control-flow primitive in
Waymark. You subclass it and decorate the subclass with @workflow, which
registers it. The definition is compiled to Waymark's intermediate
representation the first time the workflow is run or scheduled.

Calling run(...) on an instance accepts two keyword arguments beyond
your own inputs:

- `_blocking=False` queues the workflow and returns its instance id
  immediately instead of waiting for completion - the fire-and-forget
  form.
- `_priority=` is accepted and sent with the instance, but the current
  runtime does not use it.

A blocking run(...) raises `WorkflowFailedError` (whose `exception_value`
is the exception the workflow raised) if the workflow fails. It waits as
long as the workflow takes; it raises `TimeoutError` only if the server
no longer knows the instance. With `WAYMARK_SKIP_WAIT_FOR_INSTANCE` set,
a blocking run(...) queues the workflow and returns `None` without
waiting.

Under pytest, run(...) doesn't queue anything: it executes the workflow
through a bridge started without Postgres, runs its actions in the test
process, skips durable sleeps, and returns the result - so tests need no
database or `waymark-start-workers`. `_blocking` and `WAYMARK_SKIP_WAIT_FOR_INSTANCE`
have no effect there.

::: waymark.workflow.Workflow

---

## Decorator

The `@workflow` decorator registers your class under its short name - the
class attribute `name` if set, the lowercased class name otherwise - and
wraps its `run()` method. The AST compiler runs against `run()` the
first time the workflow is run or scheduled, and the resulting IR is
registered with the runtime then.

::: waymark.workflow.workflow

---

## Registry

`workflow_registry` exposes the in-process map of registered
workflows. You usually don't interact with it directly - the
`@workflow` decorator handles registration - but it's useful when
inspecting registration state or building tools on top of Waymark.

::: waymark.workflow.WorkflowRegistry
