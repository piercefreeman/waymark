# Actions

Actions are the distributed work primitive. An `@action`-decorated
async function is registered in its process's action registry, under its
module and its name - the function name, or `name=` if you pass one to
the decorator - and gets dispatched to a worker each time a workflow
calls it. Action arguments and results
round-trip through Postgres, so anything you pass needs to survive
Waymark's serializer - pydantic models, dataclasses, primitives,
containers, and common stdlib types. See
[Inputs and outputs](/python/authoring) for the full list.

## Decorator

::: waymark.actions.action

---

## Registry

The action registry is the in-process map from action name to handler,
exposed as `waymark.registry`. A worker looks the handler up there, by
module and name, each time it's asked to run an action.

::: waymark.registry.ActionRegistry

---

## Dependencies

Actions can declare dependencies the same way Mountaineer and FastAPI
controllers do - via `Annotated[T, Depends(...)]` parameters. `Depends`
is re-exported from `mountaineer-di`; the `Depend` documented below is
its backward-compatible alias with the identical signature, so import
`Depends` and read on.

::: waymark.dependencies.Depend

`provide_dependencies` resolves a function's `Depends(...)` parameters
outside a workflow - the same resolution a worker performs before it
runs an action. It's re-exported from `mountaineer-di`; pass
`dependency_overrides` to test an action against fakes.

::: waymark.dependencies.provide_dependencies

---

## Result payloads

These helpers handle the serialization layer between an action's
in-process Python objects, or a workflow's outcome, and the bytes
exchanged with the server over gRPC. Most users don't touch them
directly - the `@action` decorator handles serialization automatically -
but they're exposed for tooling that needs to interpret those payloads.

::: waymark.actions.ActionResultPayload
