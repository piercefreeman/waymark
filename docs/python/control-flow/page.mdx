# Control Flow

Anything inside a workflow's `run()` method is parsed into Waymark IR the
first time the workflow is run or scheduled, then compiled into the
program the runtime executes. The patterns below are what the compiler
recognizes today. They cover almost everything you'd actually want
to write - and where they don't, the compiler tells you up front, not at
recovery time. The few patterns that currently slip through are listed
under [Known issues](#known-issues).

Every pattern in this guide runs end-to-end against Postgres today.

## Sequential chains {{ id: 'sequential' }}

The simplest case: one action's result feeds the next.

```python
@workflow
class SequentialChainWorkflow(Workflow):
    async def run(self, text: str) -> ChainResult:
        step1 = await step_uppercase(text)
        step2 = await step_reverse(step1)
        step3 = await step_add_stars(step2)
        return await build_chain_result(text, step1, step2, step3)
```

Each `await` compiles to an action dispatch. The runtime executes them in
order, threading each result into the next action's inputs.

## Parallel fan-out {{ id: 'parallel-fan-out' }}

`asyncio.gather` is the parallel primitive. The compiler turns it into a
fan-out / fan-in pair:

```python
@workflow
class ParallelMathWorkflow(Workflow):
    async def run(self, number: int) -> ComputationResult:
        factorial_value, fib_value = await asyncio.gather(
            compute_factorial(number),
            compute_fibonacci(number),
            return_exceptions=True,
        )
        return await summarize_math(
            input_number=number,
            factorial_value=factorial_value,
            fibonacci_value=fib_value,
        )
```

`return_exceptions=True` is required - the compiler rejects a `gather`
without it. Failures propagate as values, not as raised exceptions, so a
downstream action can inspect partial results instead of losing the whole
fan-out to one bad item.

You can also spread a list comprehension into `gather` for variable-width
fan-outs:

```python
results = await asyncio.gather(
    *[send_email(to=user.email, subject="Welcome") for user in active_users],
    return_exceptions=True,
)
```

The comprehension element can be an `@action` call or a workflow helper
method - `*[self.process(item) for item in items]` fans out one helper
call per item, and each helper can await actions internally.

Empty spreads are handled correctly - a `gather` over an empty list
produces an empty result without dispatching any action invocations.

## Conditionals {{ id: 'conditionals' }}

Plain `if` / `elif` / `else` works. Each branch compiles separately; the
runtime evaluates the condition at execution time and runs only the branch
that's taken.

```python
@workflow
class ConditionalBranchWorkflow(Workflow):
    async def run(self, value: int) -> BranchResult:
        if value >= 75:
            return await evaluate_high(value)
        elif value >= 25:
            return await evaluate_medium(value)
        else:
            return await evaluate_low(value)
```

`if` without `else` also works - control flow falls through to whatever
comes next. This is the common "guard with default" shape:

```python
@workflow
class GuardFallbackWorkflow(Workflow):
    async def run(self, user: str) -> GuardFallbackResult:
        notes = await fetch_recent_notes(user)
        summary = "no notes found"
        if notes:
            summary = await summarize_notes(notes)
        return await build_guard_fallback_result(user, len(notes), summary)
```

## Loops {{ id: 'loops' }}

`for` loops process items one at a time and accumulate results. The
accumulator pattern works as expected:

```python
@workflow
class LoopProcessingWorkflow(Workflow):
    async def run(self, items: list[str]) -> LoopResult:
        processed = []
        for item in items:
            result = await process_item(item)
            processed.append(result)
        return await build_loop_result(items, processed)
```

`while` loops compile too, with `break` and `continue` working the way
you'd expect:

```python
@workflow
class WhileLoopWorkflow(Workflow):
    async def run(self, target: int) -> WhileLoopResult:
        current = 0
        iterations = 0
        while current < target:
            current = await increment_counter(current)
            iterations = iterations + 1
        return await build_while_result(
            target=target, final=current, iterations=iterations,
        )
```

## Try / except {{ id: 'try-except' }}

`try/except` is the recovery primitive. The compiler lowers the `except`
arm into a recovery path the runtime takes when the action raises a
matching exception.

```python
@workflow
class ErrorHandlingWorkflow(Workflow):
    async def run(self, should_fail: bool) -> ErrorResult:
        recovered = False
        message = ""
        try:
            result = await self.run_action(
                risky_action(should_fail),
                retry=RetryPolicy(attempts=1),  # don't retry, let it fail
            )
            message = await success_action(result)
        except IntentionalError:
            message = await recovery_action("IntentionalError was caught")
            recovered = True
        return await build_error_result(True, recovered, message)
```

Two notes:

- `self.run_action(...)` is the form to use when you want a per-call
  `retry=RetryPolicy(...)` or `timeout=`. A bare `await some_action(...)`
  uses the defaults. Note that `RetryPolicy()` with `attempts` omitted
  defaults to a budget of 100 retries; pass `attempts=1` when you want a
  failure to surface immediately.
- An `except` clause matches an exception by its class name or any of
  its base classes' names, as Python does and the same way retry policies
  do: `except OSError:` catches a `ConnectionError`, and
  `except LookupError:` catches a `KeyError`. Waymark imports nothing at
  runtime - only names are compared, so `except httpx.ConnectError:`
  means the class called `ConnectError`, whatever module it came from.
  The runtime's `ActionTimeout` and `ActionExecutionLost` derive from
  `BaseException`, so `except Exception:` does not catch them; import
  them from `waymark.vm_exceptions` to list them, or catch
  `BaseException`. `except ():` is rejected at compile time, since it
  would catch nothing.

`try/except` also works inside loops - useful for "process each item, skip
the failures":

```python
@workflow
class LoopExceptionWorkflow(Workflow):
    async def run(self, items: list[str]) -> LoopExceptionResult:
        processed: list[str] = []
        error_count = 0
        for item in items:
            try:
                result = await self.run_action(
                    process_item_may_fail(item),
                    retry=RetryPolicy(attempts=1),
                )
                processed.append(result)
            except ItemProcessingError:
                error_count = error_count + 1
        return await build_loop_exception_result(items, processed, error_count)
```

## Durable sleep {{ id: 'durable-sleep' }}

`await asyncio.sleep(seconds)` is recognized specially. It's a durable
sleep - its wake-up time is recorded in Postgres, so the sleep survives
node restarts: if the node running the workflow dies, another node picks
the instance up and it still wakes at the original time. While it sleeps,
the instance stays loaded on its node and counts toward that node's
`WAYMARK_MAX_CONCURRENT_INSTANCES`. Sleeps are woken by the node's sleep
poller, so one can wake up to one poll interval late -
`WAYMARK_SLEEP_POLL_INTERVAL_MS`, 250 ms by default. Fractional seconds
work.

```python
@workflow
class DurableSleepWorkflow(Workflow):
    async def run(self, seconds: int) -> SleepResult:
        started = await get_timestamp()
        await asyncio.sleep(seconds)  # survives worker restarts
        resumed = await get_timestamp()
        return await format_sleep_result(started, resumed, seconds)
```

This is also fine inside loops - useful for polling or for slow drip
behaviors:

```python
for i in range(iterations):
    await asyncio.sleep(sleep_seconds)
    await perform_loop_action(iteration=i + 1)
```

## Early return {{ id: 'early-return' }}

Returning from inside a branch - including from inside a loop - works:

```python
@workflow
class LoopReturnWorkflow(Workflow):
    async def run(self, items: list[int], needle: int) -> LoopReturnResult:
        checked = 0
        for value in items:
            checked += 1
            if await matches_needle(value=value, needle=needle):
                return await build_loop_return_result(
                    items=items, needle=needle,
                    found=True, value=value, checked=checked,
                )
        return await build_loop_return_result(
            items=items, needle=needle,
            found=False, value=None, checked=checked,
        )
```

## What does not compile (yet) {{ id: 'limitations' }}

The compiler refuses anything it can't lower to IR, and it tells you when
the workflow is first run or scheduled. A pattern the SDK rejects comes
with the offending line and a suggested fix; one the runtime rejects
names only what it could not lower. Waymark compiles only a deterministic
set of instructions and effects; anything outside it is rejected. The
rejected patterns:

- **f-strings.** Anywhere in the workflow body. Build formatted strings
  inside an action.
- **Calling anything but actions, the workflow's own methods, awaited
  `asyncio.sleep` and `asyncio.gather`, `len`, and `range` and
  `enumerate` as a `for` loop's iterable (`range` also assigned to a
  name or returned).** That covers other builtins like `str()` and `int()`,
  library calls like `datetime.now()` or `uuid4()`, and methods on any
  object but `self` - `Model.model_validate(...)` included (the one
  exception is `list.append`). Do that work inside an action - that's
  what actions are for.
- **Constructing classes other than pydantic models and dataclasses.**
  Models and dataclasses defined in your code can be constructed
  anywhere; any other class has to be built inside an action.
- **`raise`.** Raise inside an action; the workflow handles it with
  `try/except`.
- **`with`, `lambda`, `match`, `yield`, walrus (`:=`), `assert`, `del`,
  `global`/`nonlocal`, `import`, and nested `def` or `class`.** None of
  these have IR lowerings yet.
- **Most references to module-level globals.** Enum members and exception
  classes resolve fine; arbitrary globals don't. Pass values in through
  workflow inputs or fetch them inside an action.
- **Comprehensions outside two positions.** List and dict comprehensions
  compile when assigned directly to a variable or spread into `gather`;
  set comprehensions don't compile at all, and generator expressions
  only directly inside `gather`.
- **`gather` anywhere but a statement of its own or the right-hand side
  of an assignment.** `return await asyncio.gather(...)` doesn't compile:
  assign the result to a variable, then return it. Spreading a variable
  (`*tasks`) doesn't compile either; spread a list comprehension directly
  into the `gather`.
- **A `retry=` or `timeout=` that isn't a literal.** What compiles is a
  `RetryPolicy(...)` with keyword literals, a number or a `timedelta(...)`
  of `seconds`, `minutes`, `hours` or `days` literals, or a `self.`
  attribute assigned one of those once, at the top level of `__init__`,
  passed by keyword. Rejected, among others: a variable, a call result,
  positional `RetryPolicy` arguments, a policy passed to `run_action`
  positionally, a `self.` attribute assigned more than once or under a
  branch, a tuple for `exception_types`, a non-string or dotted entry in
  it, a timeout of zero or less, a negative backoff, either above 100
  years, and any other `run_action` keyword.
  [Retries & Timeouts](/python/retries) and the
  [RetryPolicy reference](/python/api/retry) point here for the rejected
  forms.
- **`except` with anything but an exception class in scope.** The name
  must resolve, in the workflow's module or the builtins, to an exception
  class, and a dotted name's root to a module or a class:
  `except httpx.ConnectError:` compiles and matches the class called
  `ConnectError`. An alias resolves to the class it names, so `except VE:`
  with `VE = ValueError` catches a `ValueError`. Rejected:
  `except self.error:`, `except cfg.error_cls:` with `cfg` a value, a
  class that is not an exception such as `except int:`, a value reached
  through a module such as `except os.sep:`, a tuple alias such as
  `except ERRORS:`, an undefined name, a subscript or a call as the
  handler type, and `except ():`, which would catch nothing. A name
  imported only under `TYPE_CHECKING` or inside a function is not in
  scope.

Everything in this list fails at your desk, the first time the workflow
is run or scheduled. Nothing here surfaces as a production surprise.

## Known issues {{ id: 'known-issues' }}

Waymark's guarantee is that a workflow that compiles runs as written. The
patterns below currently break it: they compile, then behave differently
from Python. Each is being closed - first by rejecting the pattern at
compile time, then by supporting it properly - and they're tracked
together in [#772](https://github.com/piercefreeman/waymark/issues/772).
Until then, avoid them.

**Compiles, then silently does something else:**

- `try/finally` and `try/else` bodies are dropped
  ([#580](https://github.com/piercefreeman/waymark/issues/580)).
- `for/else` and `while/else` bodies are dropped
  ([#581](https://github.com/piercefreeman/waymark/issues/581)).
- A chained comparison like `0 < x < 10` checks only its first comparison
  ([#582](https://github.com/piercefreeman/waymark/issues/582)).
- Assigning to a subscript, `d["k"] = v`, does nothing, so dict
  comprehensions always produce `{}`
  ([#583](https://github.com/piercefreeman/waymark/issues/583)).
- `**kwargs` and extra positional arguments in an action call, `d[k] += v`,
  and `a = b = value` are dropped or assigned wrongly
  ([#584](https://github.com/piercefreeman/waymark/issues/584)).
- `{**base, "extra": 1}` drops the spread entries
  ([#587](https://github.com/piercefreeman/waymark/issues/587)).
- `and` / `or` evaluate both sides, so an action on the right runs even
  when the left side already decided
  ([#590](https://github.com/piercefreeman/waymark/issues/590)).
- `list.append` on a list that another name also refers to - such as a
  list passed into a helper method - doesn't reach that other name
  ([#770](https://github.com/piercefreeman/waymark/issues/770)). Return
  the extended list and reassign it instead.

**Compiles, then fails at runtime where Python works:**

- `asyncio.sleep(...)` inside a `gather`
  ([#579](https://github.com/piercefreeman/waymark/issues/579)).
- A failure inside a `gather` raises out of it instead of arriving as a
  value, whatever `return_exceptions` says
  ([#575](https://github.com/piercefreeman/waymark/issues/575)).
- An `await` nested inside a larger expression, like
  `total = await a() + await b()`; await each into a variable first
  ([#585](https://github.com/piercefreeman/waymark/issues/585)).
- `isinstance(value, SomeError)` with any exception class: the SDK accepts
  it, but the runtime has no lowering for it yet and rejects the workflow
  when it is first run or scheduled
  ([#790](https://github.com/piercefreeman/waymark/issues/790)).
- Plain `self.attr` attributes: reads fail, and writes are discarded. A
  `retry=` or `timeout=` policy stored on `self` is the exception and
  works ([#586](https://github.com/piercefreeman/waymark/issues/586)).
- Mixing `int` and `float` in arithmetic or comparisons, and `/` on two
  ints that don't divide evenly, raise; `1 == 1.0` is `False`
  ([#589](https://github.com/piercefreeman/waymark/issues/589)).
- Iterating over a dict, and dict keys that aren't strings
  ([#591](https://github.com/piercefreeman/waymark/issues/591)).
- `len()` of a string counts bytes, not characters; `"-" * 20` and
  comparing lists raise
  ([#592](https://github.com/piercefreeman/waymark/issues/592)).
- Reading anything from a caught exception (`except ValueError as e:`
  then `e.args`); passing `e` to an action works
  ([#594](https://github.com/piercefreeman/waymark/issues/594)).
- `asyncio.sleep(0)`, or a negative or non-numeric duration, ends the run
  with an error ([#602](https://github.com/piercefreeman/waymark/issues/602)).

**Values change between the workflow and its actions:**

- Pydantic models and dataclasses become plain dicts inside the workflow,
  and tuples become lists
  ([#596](https://github.com/piercefreeman/waymark/issues/596)).
- `NaN` and infinities become `None`; integers of 2⁶³ and above fail
  ([#597](https://github.com/piercefreeman/waymark/issues/597)).
- An explicit `None` argument to an action is dropped, and a required
  `run()` argument the caller leaves out arrives as `None` instead of
  failing the call ([#598](https://github.com/piercefreeman/waymark/issues/598)).
- `datetime`, `Decimal`, `UUID`, `bytes`, `set` and `Enum` values lose
  their type unless the receiving parameter's annotation restores it
  ([#599](https://github.com/piercefreeman/waymark/issues/599)).
- A subclass passed where the annotation names its base class arrives as
  the base class, losing its own fields - or failing, for dataclasses. An
  unbound `TypeVar`, like `state: State[DepsT]`, loses all of them
  ([#771](https://github.com/piercefreeman/waymark/issues/771)).
